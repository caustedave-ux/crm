# WhatsApp 封号风险与防护清单

> 结论先说：**只要用非官方协议（Baileys），封号风险就不可能归零**——这是 WhatsApp 服务条款明确禁止的自动化方式。
> 能做的只有两件事：把"像机器人"的行为降到最低，以及准备好被封之后的兜底。

## 一、哪些行为会被判违规

按风险从高到低（社区与官方条款的共识，不是我们代码的猜测）：

| 行为 | 触发信号 | 我们的现状 |
| --- | --- | --- |
| 给陌生号码群发 | 短时间大量 outbound 首条消息、文案雷同 | **完全没有做群发**，只能手动一条条发 |
| 高频自动回复 | 应答间隔恒定、7×24 秒回 | **没有自动回复**，翻译只读不改写 |
| 反复注册/重连 | 同一 IP 短时间多次注册 | 已修（见下） |
| 新号立刻大量使用 | 新设备 + 高消息量 | 需要人工遵守（见第三节） |
| 多设备频繁切换 | 短时间多次登入登出 | 已加暂停/节流，避免误触 |
| 用第三方库本身 | 协议指纹、UA、行为特征 | **无法消除**，只能接受 |

## 二、我们已经做的防护（代码层）

| 防护 | 实现位置 | 说明 |
| --- | --- | --- |
| 未登录状态**不自动重连** | `src/wa.js` close 分支 | 昨晚的教训：一晚上刷了 211 次注册请求 |
| 注册间隔 ≥ 45 秒 | `MIN_ATTEMPT_GAP` | 重复点击只复用，不会重复注册 |
| 重连指数退避 | `RETRY_BACKOFF` 15s→45s→120s，最多 3 次 | 只有"登录过又掉线"才走这条 |
| 发送节流 | `sendText` 里 1s + 随机抖动 | 防连点造成机器连发特征 |
| 不做批量操作 | 全代码无群发、无自动回复、无定时发送 | 唯一出口是聊天窗的一次提交 |
| 不抢在线状态 | `markOnlineOnConnect: false` | 不让服务端以为"用户一直在线" |
| 不生成链接预览 | `generateHighQualityLinkPreview: false` | 少一次抓取请求 |
| 历史同步限量 | 最多 1500 条 | 避免首次登录拉爆 |
| 一键暂停 | 「暂停」按钮 / `wa.stop()` | 断连接但保留登录态，不自动重连 |
| 半注册状态自动清理 | connect 里检测 `creds.registered=false` | 否则会被服务器反复 401 |

## 三、必须人工遵守的纪律

1. **新号先养**：拿一个号接入后，前 3–7 天只做正常聊天（客户主动来、你正常回），别主动加陌生人。
2. **不群发、不复制粘贴同一段话**：哪怕客户问同一个问题，也改几个字。
3. **控制首条主动消息**：一小时内主动发起的新对话别超过 10 个（外贸正常跟进量远低于这个数）。
4. **别在电脑和手机之间反复切换在线状态**：这台电脑挂着就不要再用网页版登同一个号。
5. **手机端开着通知**：如果 WhatsApp 弹"你的账号可能受限/需要验证"，**立刻点「暂停」**，48 小时内不要再连。
6. **备份 `data/wa-auth/`**：里面是登录态，丢了就要重新扫码（不等于聊天记录，记录在 `data/crm.db`）。

## 四、被封之后怎么办

1. `data/wa-auth` 会失效，页面会显示「已退出登录」——不需要删数据。
2. 手机 WhatsApp 里通常有 **请求审核 / Request a review** 入口，走官方申诉。
3. 号码申诉期间：**导出导入那条路完全不受影响**（不需要协议、不联网到 WhatsApp 服务器）。
4. 决策：如果主号被限，立刻把接入切到副号，主号只做人工手机操作。

## 五、GoodJob 的做法对照（借鉴了什么、没借鉴什么）

参考项目：[huangguojia/GoodJob](https://github.com/huangguojia/GoodJob) 的 `whatsapp-plugin`（Apache-2.0）。

| 他们有 | 我们 | 说明 |
| --- | --- | --- |
| 指数退避重连（1s→2^n，上限 30s），单账号单定时器 | ✅ 已对齐思路 | 我们上限 120s、最多 3 次，更保守 |
| `logged_out` 不重连 | ✅ | 我们额外处理"配对中 401 不能当登出" |
| `markOnlineOnConnect: false`、关链接预览 | ✅ 已补 | 我们原先把预览开着 |
| 原文与译文分表存 | ✅ 等价实现 | 我们存在 `wa_messages.translated` 列 |
| 消息幂等（provider msg id 唯一） | ✅ | `UNIQUE(account_id, msg_id)` |
| AuthState 用 AES-256-GCM 加密落盘 | ❌ 没做 | 我们是明文 `creds.json`，局域网内可接受；要上公网必须补 |
| 多租户、组织级 RBAC | ❌ 不做 | 本项目是单公司内网 |
| 自动回复 / AI 客服 | ❌ **故意不做** | 这是最高封号风险的功能，你没这个需求 |
| `syncFullHistory: true` 全量历史 | ❌ 关掉了 | Baileys 7.0.0-rc14 上开这个会被直接 428 断开 |
| 官方 Meta 通道双通道 | ❌ 不接 | 官方拿不到历史记录，且按条计费 |

## 六、一句话建议

主号直连是**能跑通但不可逆**的选择：号码一旦被限，客户资源会跟着受牵连。
如果这套系统越用越重，建议最终形态是：**主号只在手机上人工操作，CRM 接入用副号**，把风险隔离在一个可替换的号码上。
